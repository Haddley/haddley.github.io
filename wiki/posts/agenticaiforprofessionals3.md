**Summary.** I built a functional interface and an MCP server for the nsw-legal-research-assistant to expose its core capabilities to both a web frontend and Claude Code. I demonstrated the system by running it through the same workflow used by Thomson Reuters to introduce CoCounsel, featuring grounded Q&A, review, and skill-chaining drafting.

## What I did
- I built a web interface and an MCP server to expose the same core skills to different clients.
- I implemented the Review and Draft skills to process legal documents.
- I integrated the Model Context Protocol to allow Claude Code to interact with the backend.
- I verified the system by running a live demo that mirrored the CoCounsel introduction.
- I ensured all components ran locally on an M4 MacBook Air without cloud dependencies.

## Claims
- The system uses a database selector to query specific legal databases.
  > "That's the reason this app has a database selector."
- The system prevents hallucinated citations by reading metadata directly from the database.
  > "The citation metadata — case name, page number — is read directly off the retrieved database row, never generated by the model, so *which* excerpt gets cited is the LLM's call, but the citation itself can't be hallucinated."
- The drafting process uses a stateless approach that forbids the model from introducing new facts.
  > "No new retrieval happens here — the exact answer and citations already on screen get passed straight back to a second LLM call, explicitly forbidden from introducing new facts or citations."
- The system provides a clear refusal when a user asks to draft from ungrounded information.
  > "That statelessness is also why the guardrail is worth testing honestly rather than cherry-picked: asking it to draft from an answer that hadn't actually established an outcome produced a correct *refusal* instead of a fabricated finding — a clean refusal on ungrounded ground is a stronger trust signal than a draft that always complies."
- The MCP tools are thin wrappers that call the exact same functions as the REST API.
  > "All three are thin wrappers calling the exact same functions the REST API and the frontend call — same skill, multiple interfaces."
- The system provides consistent results across different interfaces because they share the same backend functions.
  > "Same shape as the browser — the same mix of grounded and not-found rows across the five documents, the same reused-figures-only drafting behavior — because both interfaces are calling `review_collection()` and `draft_from_answer()` directly, not a second reimplementation of them."
- The entire stack runs locally using Docker Compose and a FastAPI backend.
  > "Every beat above ran against the full stack live on a Docker Compose setup on the M4 MacBook Air from Part 2 — Postgres/pgvector, the FastAPI backend, and the React frontend, all local, no cloud dependency for any of it:"

I built a multi-interface system that provides grounded legal research and drafting capabilities through both a web UI and an MCP server. The system successfully performs skill-chaining and produces verified citations without relying on cloud services.
